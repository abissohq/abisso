# Machine credential refresh (issue #23)

An enrolled collector renews machine authority with `POST /v1/machines/refresh`. The refresh credential is sent only as a Bearer authorization value. The JSON body contains the Keychain installation ID, the current integer credential generation, and a UUID request ID. Browser cookies and browser `Origin` requests are rejected.

Successful use rotates the refresh credential, advances its generation, resets its unused expiry to 90 days, and returns a machine access token valid for 15 minutes. Access tokens retain only `telemetry:write machine:self` authority: ingestion and machine self-service accept them, while browser read, export, and administration routes do not.

The successor is the 256-bit output of the versioned, domain-separated `abisso.machine-refresh.successor.v1` HMAC PRF. Its input binds the predecessor secret, installation ID, predecessor generation, request ID, and canonical request digest. The server persists keyed credential hashes and non-secret retry metadata, never either refresh secret. An exact retry is accepted through 30 seconds after rotation and derives the same successor. Request-wide and scheduled cleanup remove expired retry records and their metadata. A separate domain-separated keyed reuse marker retains only the family, machine, and generation association needed to revoke a late bearer; it cannot authenticate a refresh or reproduce its secret. A different request using the predecessor, or an exact retry after that boundary, revokes the complete refresh family and its issued access tokens.

An attacker with a byte-for-byte copy of the complete bearer request is indistinguishable from the collector during the 30-second retry window. This is the accepted M1 residual risk from ADR 0004; sender-constrained credentials remain out of scope until threat evidence or design-partner requirements justify them.
